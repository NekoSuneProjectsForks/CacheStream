================================================================
         HOW TO CREATE A GITHUB RELEASE TAG — v1.13.2
================================================================

STEP 1 — Go to your repository on GitHub
-----------------------------------------
Navigate to: https://github.com/cachenetworks/cachestream


STEP 2 — Open the Releases page
-----------------------------------------
On the right side of the repo homepage, click "Releases"
OR go directly to:
https://github.com/cachenetworks/cachestream/releases/new


STEP 3 — Create the tag
-----------------------------------------
In the "Choose a tag" dropdown field, type:

    v1.13.2

Then click "Create new tag: v1.13.2 on publish"
Make sure the target branch is set to: main


STEP 4 — Set the Release Title
-----------------------------------------
Paste this exactly into the title field:

    v1.13.2 — Latency & Performance Pass


STEP 5 — What to put in the description
-----------------------------------------
The description is your release notes. This is what people
see on the releases page and what gets attached to the tag.

You want to include:

  - A short summary of what changed and why
  - A bug fix section (what broke, what was the symptom,
    what was the fix)
  - A performance section (what was slow, by how much,
    what changed)
  - A list of files changed
  - The version numbers bumped

For v1.13.2, paste the formatted release notes that were
provided to you separately (the GitHub Markdown version).


STEP 6 — Mark it as latest release
-----------------------------------------
Make sure "Set as the latest release" is checked.
Do NOT check "Set as a pre-release" unless it is a beta.


STEP 7 — Publish
-----------------------------------------
Click the green "Publish release" button.

GitHub will automatically:
  - Create the tag pointing at the latest commit on main
  - Display the release on your /releases page
  - Make it available as a downloadable zip/tar.gz


================================================================
WHAT MAKES A GOOD TAG DESCRIPTION
================================================================

A tag description (annotated tag) should contain:

  1. VERSION NUMBER + CODENAME
     Clear, at the very top. Example: v1.13.2 — Latency Pass

  2. BUG FIXES (if any)
     What was broken, what the symptom was for the user,
     and what file/line was changed to fix it.

  3. PERFORMANCE IMPROVEMENTS
     What was slow, the measurable difference (e.g. 1.6s -> 200ms),
     and what changed technically.

  4. BREAKING CHANGES (if any)
     Anything that requires the user to change their .env,
     docker-compose, or config. Always flag these clearly.

  5. FILES CHANGED
     A summary list so developers can quickly see scope.

  6. VERSION BUMPS
     Which package.json files changed and from what to what.

WHAT TO AVOID IN A TAG:
  - Vague messages like "fixed stuff" or "performance update"
  - Listing every single line changed (that is what git diff is for)
  - Internal notes or TODOs meant for developers only
  - Mentioning AI tools, agents, or automation in the tag body


================================================================
QUICK REFERENCE — TAG NAMING CONVENTION
================================================================

Follow semantic versioning (semver): MAJOR.MINOR.PATCH

  MAJOR  — Breaking changes. Users must take action to upgrade.
            Example: v2.0.0

  MINOR  — New features added, fully backwards compatible.
            Example: v1.14.0

  PATCH  — Bug fixes and performance improvements only.
            No new features, no breaking changes.
            Example: v1.13.2  <-- this release

Always prefix with lowercase v: v1.13.2 (not 1.13.2)

EXAMPLE OF A WELL-WRITTEN TAG MESSAGE
================================================================

v1.13.2 — Latency & Performance Pass

Bug Fixes:
- Fixed scene switches stalling 500ms-30s due to networkidle2
  being used in setScene() instead of domcontentloaded.

Performance:
- EventSub subscriptions now parallel (1.6s -> 200ms setup)
- FFmpeg queue depth reduced from 1024 -> 32 frames
- SQLite writes faster with synchronous=NORMAL pragma
- Streamer RPC timeouts differentiated per endpoint (20s -> 5s)
- Streamer reconnect now uses exponential backoff

Files changed:
  apps/streamer/src/stream.js
  apps/web/src/lib/twitch/eventsub.ts
  apps/web/src/lib/streamer-client.ts
  apps/web/src/lib/db.ts

Version: 1.13.1 -> 1.13.2
